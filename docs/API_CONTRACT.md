# Backend API v1 — career networking

Implemented base URL: `http://127.0.0.1:8000/api/v1`. Interactive documentation: `/docs`; machine-readable schema: `/openapi.json`. All endpoints operate on one fixed `demo_user`. No user ID is accepted as an authorization mechanism.

## Recommended frontend sequence

1. Optionally POST `/onboarding/import-text` or `/onboarding/resume` to obtain suggested fields and an `import_id`.
2. Show editable fields and POST the reviewed profile to `/onboarding`. Imports do not update the profile until this call.
3. POST `/conference` with `url`, optional `name`, and `data_mode`. `fixture` (default) loads fictional sample people and never fetches the URL. `live` fetches any public event page through Bright Data. Luma pages (`https://luma.com/<event>`) use an exact parser for judges and hosts. Any other public page (Meetup, Partiful, Eventbrite, a conference speakers page) uses AI extraction (requires `KAIROS_OPENAI_API_KEY`): only people the page presents as speaker, judge, host, organizer, panelist, mentor or moderator are kept, every name must appear verbatim on the page, and titles/companies the page does not state are left blank. Guest/attendee lists are never ingested. IP addresses, localhost and internal hostnames are rejected with 422.
4. GET `/people?conference_id=...`, then save `/triage` and `/met` changes.
5. POST `/followups/{person_id}/draft`, edit, and approve for copying.

`docs/frontend-examples.json` contains responses generated by the actual application. `backend/fixtures/people.json` is ingestion seed data; it is not a full card response. Use the generated examples or live API for frontend mocks.

## Profile

```json
{
  "name": "Kiran",
  "target_roles": ["Backend engineer"],
  "skills": ["Python", "FastAPI"],
  "interests": ["Python", "Distributed systems"],
  "background": "I build backend APIs and want to work on infrastructure.",
  "location_preferences": ["San Francisco"],
  "linkedin_url": null,
  "import_id": null
}
```

Name, target_roles, and interests are required. Interests and skills are lowercased and deduplicated. Ranking currently uses interests only; target roles contextualize the goal and drafts, and skills are stored for later matching. Explicit user edits are authoritative. `linkedin_url` is an HTTPS LinkedIn URL for reference, not a scraping request. Imports perform keyword matching against a small technology vocabulary, not AI inference. Users must supply or confirm their target roles and interests.

`source` for text imports: manual, assistant_summary, resume_text. PDF imports use resume_pdf. Uploaded files are not retained; suggested fields and up to 5,000 characters of extracted background are stored locally until cleanup outside this initial API. Avoid importing unrelated personal details. There is no direct ChatGPT/Claude memory access.

## Cards and ranking

Score = distinct matching interests / selected interests, in [0,1]. Ties sort by ID. It is not a hiring probability, referral likelihood, or evidence that the person's company is hiring. Why-path edges correspond to matching topics; in FalkorDB mode those topics come from the multi-hop graph query.

Triage decisions: interesting, not_interesting, null (reset). Default discovery excludes not_interesting. Explicit filters: interesting, not_interesting, all. Fixture cards have data_mode: fixture, source: fixture, and fictional example.invalid sources with null collection dates. Live cards have data_mode: live, source: luma or web (web cards also have site and extraction: ai), event_role, the event page as their source with its real collected_at, and stale: true when served from a snapshot after a failed fetch. Live topics come from a fixed canonical vocabulary matched against each person's role text, so pick profile interests from that vocabulary (for example ai, agents, backend, infrastructure, distributed systems, data engineering, software engineering, startups). Unknown photos, fun facts, reachability, and warm intros are null. Render initials for missing photos. Do not imply these sample people attend the supplied event.

`notes` preserves all entries in timestamp order. `met` indicates a saved meeting note. Adding notes represents the user's account of the conversation. Nothing infers a meeting from a shortlist decision.

## Drafts

`kind`: introduction, follow_up, referral. Introduction does not imply a prior meeting. Follow-up requires a note. Referral requires a note and a job URL plus description; it asks conditionally, without claiming the person can refer. This is a deliberate initial product constraint.

`generation`: `auto` (default), `ai`, or `template`.

- `auto`: uses OpenAI when `KAIROS_OPENAI_API_KEY` is set. If the provider fails, returns a template draft with `generation_mode: template` and a `generation_note` giving the reason. A template is never labeled as AI.
- `ai`: OpenAI only. 503 if not configured, 502 if the provider fails. No draft is saved on failure.
- `template`: deterministic template, no model call.

`generation_mode` is `ai` or `template`; `model` names the OpenAI model for AI drafts and is null otherwise. `grounded_on` lists everything the draft was generated from (profile, person, notes, user-supplied job). `cited` lists the ids the model says it used, filtered to ids that were actually provided. AI drafts receive all of this person's notes for follow-ups and referrals and no notes for introductions. Templates use the latest note only. Users review before copying. Approval is persisted, never sent. Editing an approved draft resets its status to draft.

## Operational boundaries

Fixture loading is synchronous and returns 201 with stage ready, not the earlier proposed 202 asynchronous scrape. A failed/interrupted load marks the conference failed; cards are unavailable for it. Live loading is also synchronous. Each successful fetch is snapshotted per event and reused for `KAIROS_SNAPSHOT_MAX_AGE_HOURS` (default 24). If a fetch fails, the last snapshot is used and marked stale; with no snapshot the request fails with 502. Live mode never falls back to fixtures. Conference `freshness` is `live` (fetched now), `cache` (fresh snapshot reused, no fetch) or `stale` (fetch failed, last snapshot served). A first load of a large non-Luma page can take up to about a minute while the AI reads it, so give POST /conference a long client timeout and show a loading state; repeat loads are instant from cache. `GET /health` reports `live_sources`: `["luma"]` with Bright Data only, `["luma", "any_public_page"]` when OpenAI is also configured.

422: invalid input, missing job data, or a non-public live URL; 404: unknown or cross-conference IDs; 409: missing onboarding/note or not-ready conference; 413: oversized upload; 401: missing/wrong configured API key; 502: live event fetch failed with no snapshot, or explicit AI drafting failed; 503: graph connection errors, AI drafting requested but not configured, or a non-Luma live page without OpenAI configured. Error bodies use `detail`.

Local demo only: CORS is configured for one exact frontend origin; it is not authentication. Optional X-API-Key is a shared team credential. Multi-user sessions, per-user authorization, deletion/export controls, and hardened document parsing are prerequisites to public deployment.

### Event list

`counts.interesting` = people triaged interesting; `counts.met` = distinct people with at least one meeting note; `counts.drafts_pending` = drafts not yet approved. `start_at`/`end_at` come from the event page for live Luma events and are null for fixture events, so a client can bucket now/upcoming/past only when dates exist.

### Voice notes

Record in the browser with `MediaRecorder` (Chrome/Android produce webm, iOS Safari mp4) and POST the blob to `/voice/transcribe`. Speech-to-text uses OpenAI `gpt-transcribe` (configurable via `KAIROS_OPENAI_TRANSCRIBE_MODEL`); audio is forwarded once and never stored. The response is text to review: put it in the note box, let the user edit, then save with POST `/met`. With `conference_id` and no `person_id` (mic tapped from any screen), `person_candidates` lists people named in the note by full name or by a first name only one person at the event has, so the app can ask "Is this about Kaushal?". 503 without `KAIROS_OPENAI_API_KEY`, 422 for unsupported/empty audio or no speech, 413 over 10 MB, 502 on provider failure. Microphone access requires a secure context: `localhost` works on the laptop; a phone needs an https URL (for example a tunnel), not `http://<laptop-ip>`.

### Graph memory (FalkorDB)

People are linked to companies with `(Person)-[:WORKS_AT]->(Company)` and carry a normalized `name_key`. `GET /people/{id}/memory` walks the graph from that person to (1) the same person at other events (`SAME_PERSON`) and (2) colleagues at the same company at any event (`WORKS_AT → Company ← WORKS_AT`), and returns only the user's own recorded interactions with them: meeting notes and approved messages. Appearing at the same company is not memory by itself. Each item carries the graph `path` that produced it. AI drafts receive these items as `memory` context, may mention the most relevant one, cite it in `grounded_on` (type `memory`, with `path`), and must not claim a colleague endorsed or referred the user. SQLite mode computes the same relations in Python.

### Authentication and usage limits

With `KAIROS_AUTH_MODE=clerk` (the default), every `/api/v1` request needs a Clerk session token, sent as `Authorization: Bearer <token>` (or the same-origin `__session` cookie). The backend verifies its RS256 signature against the Clerk instance's JWKS, `exp`/`nbf`, the issuer, and `azp` against the allowed origins; the user is the `sub` claim. Missing or invalid tokens get 401. Each user has their own graph, so profiles, events, notes, drafts and memory never cross users. `/health` stays public. `KAIROS_AUTH_MODE=none` is for local development and tests only: one local user, optional shared `X-API-Key`.

Regular users have daily limits; admins (verified emails in `KAIROS_ADMIN_EMAILS`) have none. Over a limit the API answers 429 with a readable `detail` and `Retry-After`:

| Limit | Default | Counts |
| --- | --- | --- |
| New events per user per day | 3 | Only fresh Bright Data fetches; cached events are free |
| New events per day, all regular users | 30 | Same, shared ceiling protecting Bright Data credits |
| AI drafts per user per day | 20 | AI generation only; template drafts are free |
| Voice notes per user per day | 30 | Transcriptions |
| Requests per user per minute | 120 | Every authenticated call |

`GET /me` returns `{user_id, admin, usage}` where `usage` is `{event_fetch, draft, voice}` each `{used, limit}` (null for admins). Counters live in FalkorDB (Redis) and survive restarts.
